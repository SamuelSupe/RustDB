# RustDB v0.6.0-alpha.1 目标

状态：v0.6 完整路线图；`v0.6.0-alpha.1` 先交付可靠性切片
原则：可靠性优先，不进行 DuckDB 性能对比，不做重复或极端性能压力测试。

## alpha.1 当前收敛范围

本阶段先完成以下闭环：持久 `Engine` 和 Catalog generation、CSV/Parquet
流式导入、Native 不可变 segment、`CREATE TABLE AS`、append、整表替换、
查询快照、原子提交、重启恢复、旧快照回收、磁盘硬配额、本地备份恢复、
整数/Decimal `SUM` 扩宽，以及确定性的基础基数/输出内存估算。

S3/MinIO 仍可作为 CSV/Parquet 导入源，但 S3/MinIO 备份目标、Native
列级 NDV/Top-K/直方图、最多 8 表 DP Join 枚举、完整物理计划分层、大型
`IN` 紧凑表达式和 CTE 成本物化不作为 alpha.1 的完成条件，继续留在后续
v0.6 alpha。alpha.1 只做定向可靠性验证；发布候选时再执行一次完整
OrbStack 验证。

## 目标

完成可作为唯一数据副本的本地 Native 列式存储，使 CSV 和 Parquet 数据能够被流式导入、持久保存、原子发布、并发读取、崩溃恢复和一致性备份。

同时建立后续性能优化所需的持久统计信息、物理计划和 CBO 基础。v0.6 不承担超过 DuckDB 的性能门槛。

## v0.6 完整目标（分 alpha 交付）

### 1. 持久 Engine 与 Catalog

- 新增持久数据库打开方式，同时保留当前临时 Engine 模式。
- 持久保存表、schema、segment 清单、统计信息和 format version。
- Catalog 与 manifest 损坏时返回结构化错误，不猜测或静默忽略。
- 未知目录和文件不会被恢复清理流程误删。

### 2. Native 列式存储

- 从本地或 S3/MinIO CSV、Parquet 流式导入。
- 支持原子首次导入、批量追加和整表替换。
- 使用不可变 column segment 和版本化磁盘格式。
- 每个 segment/page 保存 checksum、行数、NULL 数、min/max、字节大小和必要的 CBO 统计。
- 编码保持简单且可独立验证，覆盖 plain、dictionary、RLE、delta/bit-packed 和通用压缩回退。
- 扫描只读取所需列，并使用 segment/page 统计进行安全裁剪。

### 3. 原子提交与快照

- segment 完整写入并校验后才能进入 manifest。
- 文件、manifest 和目录按正确顺序执行 fsync，最后原子切换当前 generation。
- 导入、追加或替换期间，已开始查询继续读取旧快照。
- 提交完成后，新查询读取新快照。
- 任何查询都不能观察到半提交表。
- 旧 segment 仅在没有查询持有对应快照后才能回收。

### 4. 崩溃恢复

- 已成功提交的数据能够承受进程崩溃和操作系统重启。
- 恢复只能选择 checksum 和引用关系完整的已提交 generation。
- 提交各阶段的中断均保留上一版本可读。
- 只清理带 RustDB marker 且确认未提交的 staging/orphan 文件。
- 恢复和清理可重复执行并保持幂等。

### 5. 备份与恢复

- 对固定 manifest 快照执行一致性备份。
- 支持备份到其他本地目录或 S3/MinIO。
- 恢复后 schema、行数和查询 checksum 必须一致。
- 不承诺磁盘硬件损坏后的自动恢复、复制或高可用。

### 6. CBO 与正确性基础

- 将逻辑优化和物理计划分离。
- Native 表提供 row count、null count、min/max、近似 NDV、Top-K 或有界直方图等统计。
- 最多 8 表使用动态规划 Join 枚举，更大 Join 图使用简单贪心回退。
- EXPLAIN ANALYZE 展示估算基数和实际基数，便于后续校准。
- 修复 SUM 结果类型扩宽，避免宽累加器在输出时错误收窄。
- 大型 IN 使用紧凑集合表达式，不展开为长 OR 树。
- 物理列映射不保留无用逻辑列，也不创建无意义的 NULL 数组。
- 重复 CTE 可在成本合适时物化并复用。

## 数据与磁盘边界

- Native 数据在导入成功后允许删除原始 CSV/Parquet，并长期作为唯一副本。
- v0.6 只支持不可变 segment 的批量导入、追加和整表替换。
- 不支持行级 UPDATE、DELETE、行级 MVCC 和通用事务。
- 最终 Native 数据、索引和 Catalog 不超过源数据大小的 2.0 倍，另为每张表保留最多 64 KiB 的固定格式元数据额度，以支持小表和空表。
- 导入采用流式写入，不创建第二份完整临时数据副本。
- 导入期间包含源文件的峰值磁盘占用不超过源数据大小的 3.0 倍，另加同一份每表 64 KiB 固定格式元数据额度。
- 高压缩输入若无法满足最终 2.0 倍限制，导入必须返回明确的资源错误，不能突破限制。
- append/replace 的预检必须同时计算旧快照、源数据和新 segment；预计或实际超过 3.0 倍峰值时拒绝操作。不能为了保留旧快照和完成替换而静默放宽上限。

## 可靠性验收

- CSV 和 Parquet 从本地、MinIO 导入后的 Native 结果与预置 golden checksum 一致。
- 首次导入、追加、整表替换和重复打开数据库均保持 schema 与数据一致。
- 对提交关键阶段进行确定性故障注入，重启后只出现旧版本或新版本。
- 并发读与导入/替换验证 manifest 快照隔离。
- 备份恢复后表定义、行数和代表性查询 checksum 一致。
- 损坏 segment、manifest、checksum 和不完整备份均返回明确错误。
- 成功、错误、取消和恢复结束后，task、reservation、snapshot、staging 和临时文件全部归零。
- 磁盘占用严格满足最终 2.0 倍和导入峰值 3.0 倍限制，以及每表最多 64 KiB 的固定格式元数据额度。

## 轻量验证策略

- 开发期间只运行与当前模块直接相关的测试。
- 发布候选完成后运行一次完整 OrbStack fmt、Clippy、build、unit、integration、MinIO、recovery 和 release 验证。
- 只保留一个 2 GiB 资源/Spill 冒烟场景。
- 只使用小型数据做一次 1/4 线程性能 sanity check，确认没有明显串行化或数量级回退。
- 不运行 DuckDB timing comparison、TPC-H SF100、ClickBench 100M、JOB 性能门禁或重复低内存 soak。

## 实施顺序

1. 持久 Engine 配置、数据库目录布局和 format-version marker。
2. Catalog、manifest generation 和原子提交。
3. Native segment writer/reader、checksum、统计信息和 Scan 集成。
4. CSV/Parquet 流式导入、追加和整表替换。
5. 快照固定、清理、重启恢复和故障注入。
6. 备份恢复与磁盘记账。
7. CBO 统计基础和指定正确性修复。
8. 一次最终 OrbStack 可靠性验收和轻量资源冒烟检查。

## 明确不属于 v0.6

- 与 DuckDB 的性能胜负和硬性能门槛。
- v0.7 的内部 selection-vector 执行、Join/Aggregate 热路径重写和全局工作窃取调度器。
- Iceberg、JSON、ORC、其他 Lake 格式和 Parquet 写入。
- 行级 DML、MVCC、复制、高可用、分布式执行和服务协议。
- 与当前可靠性目标无关的大范围 SQL 功能扩展。

## 实现约束

- 单体文件保持较小，模块职责单一。
- 优先使用简洁直接的实现，不建立框架式过度抽象。
- 继续禁止项目自身使用 unsafe，不引入 DataFusion。
- 最终验证默认使用 OrbStack。
